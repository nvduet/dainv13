Bài 0C · Claude Code cơ bản

Thời lượng đọc + thực hành ~4 giờ · chuẩn bị cho BT-1, BT-2 và buổi thực hành tuần 1–4

Bài này cho bạn đủ Claude Code để làm bài tập từ tuần 1. Chỉ phần CƠ bản: cài đặt, chạy, giao việc, đọc kết quả. Phần nâng cao (hooks, permission, quản trị tập trung) để dành gói pre-work tuần 5, vì các thứ đó chỉ có nghĩa sau khi bạn học tam phân ở D1 — biết việc nào thuộc nhóm "xác định" thì mới biết cái gì cần ràng buộc cứng.
Đây là tài liệu thực hành: đọc đến đâu làm đến đó trên máy của bạn. Cuối tập có checklist "sẵn sàng cho tuần 1".

1 · Claude Code là gì, và khi nào dùng

Claude Code là công cụ AI chạy trong terminal, thao tác trực tiếp trên thư mục mã nguồn của bạn: đọc file, sửa file, chạy lệnh, chạy test. Khác với chat trên web (bạn copy-paste code vào), Claude Code làm việc ngay trong dự án — nó thấy cấu trúc thư mục, chạy được lệnh, và sửa file tại chỗ.

Trong khóa này bạn dùng Claude Code cho phần công việc chạm vào codebase: viết validator (BT-3), xây workflow (BT-4), thử nghiệm trên dự án thật. Chat web vẫn dùng cho phân tích, soạn tài liệu, brainstorm — hai công cụ, hai việc.

Nhắc lại từ Bài 0B: đây là một agent, chạy vòng lặp nhận bối cảnh → quyết định → hành động → đọc kết quả. Claude Code chỉ khác ở chỗ hành động của nó là thao tác lên file và lệnh thật.

2 · Cài đặt và phiên làm việc đầu tiên

Cài đặt

Cài Claude Code theo hướng dẫn chính thức (yêu cầu Node.js). Sau khi cài, mở terminal trong thư mục dự án và gõ claude để bắt đầu một phiên.

Phiên làm việc

Một phiên Claude Code là một cuộc hội thoại có trạng thái, trong đó agent nhớ những gì đã làm trong phiên. Bạn gõ yêu cầu bằng tiếng Việt hoặc tiếng Anh, agent thực hiện, báo kết quả, chờ yêu cầu tiếp theo.

Ba thao tác cơ bản của một phiên:

  • Giao một task nhỏ: "đọc file X và tóm tắt cấu trúc của nó" — agent đọc và trả lời.
  • Yêu cầu thay đổi: "thêm hàm kiểm tra Y vào file Z" — agent sửa file, cho bạn xem thay đổi trước khi áp dụng.
  • Chạy và kiểm: "chạy test và cho biết kết quả" — agent chạy, đọc output, báo lại.

Nguyên tắc an toàn ngay từ đầu (sẽ học kỹ ở D3): agent hỏi bạn trước khi làm việc có hậu quả. Đừng bấm "đồng ý tất cả" theo phản xạ — đọc xem nó định làm gì. Ba luật cứng của khóa áp dụng ngay: agent không tự push/merge/release, không đụng file bí mật (.env), và đang chờ duyệt thì không tự đánh dấu hoàn thành.

3 · File CLAUDE.md

claude.md là file đặt trong dự án, chứa bối cảnh mà bạn muốn agent luôn biết: quy ước code của dự án, cấu trúc thư mục, những điều cần lưu ý. Mỗi phiên Claude Code tự đọc file này.

Phải nhớ ngay (và sẽ nhấn lại ở D3): Claude.md là gợi ý, không phải ràng buộc cứng. Bạn viết "đừng sửa thư mục config" trong claude.md — agent thường tuân theo, nhưng đó là hướng dẫn thêm vào bối cảnh, không có gì đảm bảo tuyệt đối. Ràng buộc cứng (permission deny) là chuyện của gói nâng cao tuần 5. Ở tuần 0, bạn dùng claude.md để cho agent biết về dự án, không dùng nó để chặn điều nguy hiểm.

Một claude.md cơ bản nên có: mô tả ngắn dự án làm gì, ngôn ngữ và framework chính, quy ước đặt tên, và cách chạy test. Viết ngắn gọn — nhồi quá nhiều thì loãng (nhớ giới hạn context ở bài 0B).

Ví dụ · CLAUDE.md mười dòng đủ dùng

# Dự án: demo AAOS-CDC
## Lệnh hay dùng
- Test:  uv run pytest -q
- Lint:  uv run ruff check .
## Quy ước
- Tên property vendor: VENDOR_<NHÓM>_<TÊN>, xem rules/naming.md
- KHÔNG sửa file trong generated/ — sinh tự động từ spec
## Khi không chắc
- Hỏi trước khi đổi API public; nêu 2 phương án kèm trade-off

Ngắn thế này là đủ cho tuần đầu — CLAUDE.md tốt lớn dần theo dự án, không viết một lần cho xong.

4 · Giao task và đọc kết quả

Giao task tốt = C-T-R áp vào code

Áp công thức C-T-R từ Bài 0B vào bối cảnh code:

  • Context: file/thư mục nào liên quan, quy ước gì cần theo (thường đã ở claude.md).
  • Task: việc cụ thể — "viết", "sửa", "kiểm", "refactor".
  • Rules: ràng buộc — "không đổi api công khai", "giữ style hiện tại", "thêm test cho thay đổi".

Task mơ hồ ("cải thiện file này") cho kết quả mơ hồ. Task rõ ("thêm kiểm tra null cho tham số đầu vào của hàm parse, kèm test") cho kết quả dùng được.

Đọc kết quả có phán đoán

Đây là chữ D — Discernment — áp vào code. Agent sửa xong, cho bạn xem thay đổi. Đừng chấp nhận mù:

  • Thay đổi có đúng ý không, hay agent hiểu lệch?
  • Nó có sửa thừa thứ bạn không yêu cầu không?
  • Test có thật sự chạy và pass không, hay agent chỉ *nói* là pass? (Đọc output test thật.)

Nhắc lại nguyên tắc bài 0B: AI viết code mượt không đồng nghĩa với code đúng. Chuyên môn của bạn là công cụ thẩm định — không có nó, bạn dễ chấp nhận code kém.

Vì sao quan trọng với SA/PTL: Claude Code là công cụ bạn dùng cho mọi bài tập chạm code từ tuần 1 (BT-1, BT-2) đến workflow lớn (BT-4). Nắm mức cơ bản ở tuần 0 nghĩa là tuần 1 bạn tập trung vào TƯ Duy phân loại việc, không vật lộn với công cụ.

Ví dụ · năm phút đầu tiên của một phiên tốt

Mở phiên trong thư mục repo → gõ /init nếu dự án chưa có CLAUDE.md (agent tự đọc repo và đề xuất bản đầu) → giao việc đầu tiên NHỎ và kiểm được: "chạy bộ test, cho tôi danh sách test đang fail kèm lý do một dòng mỗi cái". Việc nhỏ này làm ba nhiệm vụ cùng lúc: kiểm môi trường chạy được, kiểm agent hiểu repo, và cho bạn thấy cách nó trình bày — trước khi giao việc có rủi ro thật.

5 · Bài thực hành mẫu: prompt → diff → test evidence → review notes

Ghép mục 4 thành một vòng hoàn chỉnh. Task prompt cho coding agent cần ba phần: context (module, điểm bắt đầu, quy ước), constraint (phạm vi được đụng, điều cấm) và acceptance criteria (tiêu chí nghiệm thu kiểm được — "thế nào là xong"). Thiếu acceptance criteria, agent dừng ở "có vẻ ổn" (Bài 0B).

Context: module cluster/speed/, hàm update_speed() đọc VehicleSpeed qua lớp adapter vhal/.
Task: nếu signal không cập nhật quá 500 ms (giá trị giả định), hiển thị "--" thay vì giữ số cũ.
Constraint: chỉ sửa cluster/speed/ và test tương ứng; không đổi API public;
  không đọc VHAL trực tiếp; KHÔNG sửa expectation của test cũ; không chắc thì hỏi.
Acceptance criteria: có test mới cho ca timeout, fail trước khi sửa và pass sau khi sửa;
  toàn bộ test của module pass; diff không có file ngoài phạm vi.

Review diff và test output

  • Diff: đọc từng file — đúng ý hay hiểu lệch? Có file ngoài phạm vi, sửa thừa, đổi format hàng loạt không? Có đi đúng kiến trúc (qua adapter) không?
  • Test: tự chạy hoặc đọc output thật (lệnh, số test chạy, pass/fail) — câu "test đã pass" của agent không phải bằng chứng. Cảnh giác khi test cũ bị sửa expectation, bị xóa hoặc bị skip để "xanh": test đó có thể đang bảo vệ một behavior đúng.
Bằng chứng giữ lạiNội dung
Promptnguyên văn, có context, constraint, acceptance criteria
Diffdiff thật agent tạo (và bản sau khi bạn sửa, nếu có)
Test evidencelệnh chạy + output do bạn tự đọc, trước và sau thay đổi
Review notesđạt/chưa đạt theo từng acceptance criteria, chỗ agent sai và cách sửa, ai quyết định chấp nhận

6 · Quản lý phiên làm việc

Phiên (session) có bộ nhớ riêng: mọi thứ hai bên nói và mọi kết quả tool đều nằm trong context của phiên. Ba hệ quả thực dụng:

  • Phiên dài tự làm mình kém đi. Kết quả tool cũ, các lần thử sai, thảo luận lan man — tất cả chiếm chỗ và gây nhiễu. Dấu hiệu cần /clear: agent bắt đầu lặp lại lỗi đã sửa, hoặc nhắc tới việc đã xong từ lâu.
  • Một phiên một việc. Trộn "sửa bug HVAC" với "soạn slide báo cáo" trong một phiên nghĩa là context hai việc nhiễu nhau. Mở phiên mới rẻ hơn nhiều so với gỡ nhiễu.
  • Nén có mất mát. Khi phiên chạm trần, công cụ tự tóm tắt phần cũ (compact) — chi tiết bị mất là chi tiết bạn không chọn. Việc quan trọng: chủ động chốt lại quyết định vào file (CLAUDE.md, ghi chú) trước khi phiên dài, đừng phó mặc cho tóm tắt tự động.

Người thạo phân biệt rõ hai loại trí nhớ: trí nhớ phiên (tự mất, không kiểm soát được lúc nén) và trí nhớ dự án (CLAUDE.md — bền, do mình chủ động viết). Nguyên tắc: điều gì mai vẫn cần đúng thì phải nằm trong file, không nằm trong phiên.

7 · Hai chế độ kiểm soát hành động

Claude Code cho chọn mức kiểm soát mỗi hành động. Hai chế độ đáng nắm ngay tuần đầu:

  • Chế độ lập kế hoạch trước (plan mode): agent trình kế hoạch các bước, bạn duyệt rồi nó mới làm. Hợp với: việc chạm nhiều file, việc lần đầu làm loại này, việc bạn chưa tin tay agent. Chi phí: thêm một nhịp chờ — đáng giá khi giá của bước sai lớn hơn giá của nhịp chờ.
  • Chế độ chạy liền tay: hành động trong vùng allow chạy không hỏi. Hợp với: vòng lặp sửa-test quen thuộc trong vùng permission đã cấu hình chặt. Điều kiện tiên quyết: vùng deny phải dựng xong TRƯỚC — tốc độ chỉ an toàn khi hàng rào có trước tốc độ.

Sai lầm tuần đầu phổ biến: bật chạy-liền-tay vì "hỏi hoài phiền" khi chưa cấu hình deny, tức là đổi phiền lấy rủi ro. Thứ tự đúng ngược lại: chịu phiền một buổi để dựng permission, rồi mới mở tốc độ.

8 · Cách agent đọc một repo lớn

Repo AAOS hàng triệu dòng không nhét vừa bất kỳ cửa sổ context nào — vậy agent "hiểu" codebase bằng cách nào? Nó làm gần giống kỹ sư mới vào dự án: tìm kiếm theo từ khóa (grep), liệt kê theo mẫu tên file (glob), rồi đọc chọn lọc đúng file nghi liên quan. Hiểu cơ chế này, bạn biết luôn giới hạn và cách giúp:

  • Giới hạn 1 — tìm theo chữ, không theo nghĩa: hỏi "chỗ nào xử lý nhiệt độ ghế" mà code đặt tên seat_thermal thì tìm "temperature" trượt. Cách giúp: ghi bản đồ thuật ngữ vào CLAUDE.md — "nhiệt độ ghế → seat_thermal, module hvac/".
  • Giới hạn 2 — không thấy kiến trúc ngầm: quy ước "mọi thay đổi VHAL phải qua lớp adapter" không nằm trong file nào cả, nó nằm trong đầu kiến trúc sư. Agent sẽ sửa thẳng nơi grep dẫn tới — đúng cú pháp, sai kiến trúc. Cách giúp: một mục "bản đồ module + luật đi lại giữa các tầng" trong CLAUDE.md đáng giá hơn mọi lời dặn miệng.
  • Giới hạn 3 — chi phí thăm dò: mỗi vòng tìm-đọc tốn thời gian và token; repo càng lạ, vòng càng nhiều. Cách giúp: khi giao việc, trỏ thẳng điểm bắt đầu ("liên quan chủ yếu tới hal/hvac/ và test tương ứng") — một dòng của bạn tiết kiệm mười vòng thăm dò của nó.

Quy luật chung rút ra: agent làm việc tốt trên repo có cấu trúc mà NGƯỜI MỚI cũng làm việc tốt. Đầu tư vào bản đồ codebase phục vụ cả hai đối tượng cùng lúc — thêm một lý do khoản đầu tư này đáng giá độc lập với chuyện AI.

Câu hỏi nghiền ngẫm (mang đến buổi thực hành tuần 1)

  1. Điều gì trong dự án của bạn thuộc loại "mai vẫn cần đúng", và hiện nó đang nằm ở đâu: đầu người, chat log, hay file?
  2. Việc nào bạn định giao agent tuần này xứng đáng plan mode? Giá của một bước sai ở việc đó là gì?
  3. Nếu CLAUDE.md của repo do 5 người cùng sửa, quy tắc nào cần có để nó không thành bãi rác chung?

Checklist "sẵn sàng cho tuần 1"

Trước buổi D0, đảm bảo bạn đã làm được cả năm việc sau trên máy của mình:

  • ☐ Cài xong Claude Code, chạy claude mở được một phiên
  • ☐ Giao được một task đọc-và-tóm-tắt trên một file thật của dự án
  • ☐ Yêu cầu được một thay đổi nhỏ và xem được diff trước khi áp dụng
  • ☐ Tạo được một file claude.md cơ bản cho dự án của mình
  • ☐ Chạy được test qua Claude Code và tự đọc output test (không chỉ tin lời agent)

Làm được năm việc này nghĩa là bạn đủ công cụ để bắt đầu BT-1 và BT-2. Phần sâu hơn — vì sao gợi ý khác ràng buộc, hooks chặn thế nào, quản trị cho cả đội — sẽ đến ở D3 sau khi bạn đã có tư duy tam phân.
